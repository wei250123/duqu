# Duqu Gateway Upgrade Roadmap

本文按“先打稳核心、再扩展运维入口、最后做平台化和硬件迁移”排列升级顺序。
项目现有 Python/PyQt6 版本继续作为参考实现和功能基线；嵌入式开发板移植单独
立项，等桌面/服务端核心能力和协议契约稳定后再启动。

## 当前定位

Duqu 是一个离线优先的工业边缘采集网关，负责 Modbus 数据采集、边缘处理、
本地持久化、MQTT 上行和运行状态观测。架构目标是让同一套核心运行时可由
桌面 UI、Web 控制台和未来的无界面服务入口使用。

## 路线总览

| 阶段 | 目标 | 状态 |
| --- | --- | --- |
| 0. 基础可靠性 | 配置/缓存/SQLite/认证安全、CI、数据保留 | 已完成第一轮，仍需覆盖压力和异常场景 |
| 1. 架构边界 | `GatewayRuntime` 统一后台服务生命周期，记录模块依赖规则 | 已完成 |
| 2. Web 运维入口 | 浏览器监控设备、MQTT、离线队列和死信；统一调用现有 API | 本次实现基础版 |
| 3. API 与权限 | 登录令牌、角色授权、审计、配置/控制 API、OpenAPI 契约 | 待做；当前状态 API 只读，Token 为部署级访问令牌 |
| 4. 工业可靠性 | 协议模拟器、断网/断电/磁盘满故障注入、性能和长稳测试 | 待做 |
| 5. 部署与升级 | Windows 服务、PyInstaller、安装/卸载、备份恢复、版本迁移 | 待做 |
| 6. 生态与集成 | Web 管理配置、告警通知、Prometheus/Grafana 示例、Webhook | 待做 |
| 7. 嵌入式移植 | MCU/SoC、RTOS、HAL/BSP、Flash 队列、HIL 和 OTA | 后续项目；先保留架构提示词和兼容矩阵 |

## 阶段 0：基础可靠性

已具备账户持久化与角色权限、密码哈希、AES-GCM、MQTT TLS 校验、断网缓存
重试/死信、SQLite 迁移和 busy timeout、采集数据保留、GitHub Actions 与基本
单元测试。下一步补齐：

- MQTT 用户名与密码在本地配置中的加密存储及导出脱敏；
- 登录失败锁定、会话超时和安全审计；
- 缓存容量、SQLite 并发、配置损坏、磁盘空间不足等边界测试；
- Lua 和表达式执行的超时、资源限制及隔离策略评估。

## 阶段 1：架构边界

后台服务生命周期集中在 `core/runtime/GatewayRuntime`；协议、采集、处理、存储、
安全、API、UI 的职责边界见 [ARCHITECTURE.md](ARCHITECTURE.md)。新增后台 worker
必须由 runtime 启停，UI 不直接持有底层线程或数据库生命周期。

## 阶段 2：Web 运维入口

本轮提供只读 Web 监控页面，读取 `/api/v1/status`，展示网关健康、设备运行状态、
通信和上传成功率、最近通信时间、缓存待补传和死信计数。页面静态资源与标准库
HTTP API 一起服务，不新增前端框架和运行时依赖。

后续增强顺序：

1. 将在线/离线、报警和缓存积压趋势接入历史查询 API；
2. 增加设备详情、点位最新值和报警列表；
3. 设计用户登录与短时访问令牌，按 RBAC 授权远程访问；
4. 增加设备配置编辑、连接测试、采集启停和缓存重放等操作；
5. 每个写操作都要有输入 schema、权限检查、幂等策略、操作审计和 CSRF/重放防护；
6. 在写 API 完成之前保持当前 Web 页面只读。

## 阶段 3：API 与权限

- 版本化 API schema，统一错误码、分页、过滤和时间戳语义；
- 用用户身份和角色权限替换单一部署级 Token；
- 明确本机、局域网和反向代理部署模式。远程访问必须经 HTTPS 或可信 TLS 代理；
- 设置连接、请求体和并发上限，避免慢客户端拖住网关线程；
- 为 API 建立兼容性测试和可导出的 OpenAPI 文档。

## 阶段 4：工业可靠性

- 用虚拟 Modbus RTU/TCP 设备覆盖异常帧、超时、CRC 错误和重连；
- 注入 MQTT broker 断连、认证失败、证书过期和发布超时；
- 注入进程退出、机器重启、磁盘满、数据库锁和缓存满；
- 核对至少一次上传语义，并为接收端提供消息唯一 ID/幂等字段；
- 建立数据采集速率、缓存增长、恢复吞吐和 API 延迟的基准；
- 在目标现场运行 24/72 小时 soak 测试，记录内存、线程、数据库和队列趋势。

## 阶段 5：部署与升级

- PyInstaller 构建和干净 Windows 虚拟机安装测试；
- 后台服务模式与桌面控制台分离，服务重启和日志轮转有明确策略；
- 配置 schema 版本化，升级前自动备份，失败可恢复；
- 安装包签名、版本号、变更日志、校验和与可回滚发布；
- 设计配置备份/恢复向导，秘密材料单独处理，不放入普通导出包。

## 阶段 6：生态与集成

- 提供 Prometheus 抓取和 Grafana Dashboard 示例；
- 告警支持邮件、Webhook 或企业消息通道，并提供降噪/恢复通知；
- 暴露只读集成 API、设备模板和可导入导出的配置 schema；
- 为第三方协议插件定义版本化接口、权限边界和兼容性声明。

## 阶段 7：嵌入式开发板移植

这是后续单独阶段，待现有功能和消息契约稳定后启动。开始前至少确定板卡型号、
芯片、SDK/RTOS、串口/RS-485/网络硬件、Flash/RAM、外部存储、采集速率和离线时长。
移植提示词已记录在 [EMBEDDED_PORTING_ARCHITECT_PROMPT.md](EMBEDDED_PORTING_ARCHITECT_PROMPT.md)。

嵌入式工作分为平台无关核心、Ports/HAL、BSP、真实驱动、HIL/长稳和 OTA 回滚，
不把 PyQt、SQLite、Lua 或桌面 HTTP 服务直接搬入 MCU。未知板卡信息必须显式登记，
禁止猜测引脚、时钟、分区或驱动 API。

## 建议的下一批实现顺序

1. 为 Web 增加设备详情、报警历史和数据趋势只读 API；
2. 把当前部署 Token 升级为登录会话和 RBAC API 权限；
3. 建立 Modbus/MQTT 可重复故障模拟测试；
4. 增加版本化配置迁移、备份和恢复；
5. 做 PyInstaller/Windows 服务部署；
6. 核心行为稳定后，再按嵌入式提示词启动目标板移植。

## 发布门槛

每次升级至少满足：单元测试通过、静态编译检查通过、配置迁移兼容、秘密未进入
仓库、启动与清理路径可重复执行。涉及协议、存储和网络恢复的版本还必须带模拟
故障测试。没有真实硬件的测试结果必须标注为 host/fake，不得冒称 HIL 或现场验证。
